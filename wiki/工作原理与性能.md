# 工作原理与性能

本文是面向阅读与维护者的技术文档：解释 blocksync 的整体架构、索引的二进制格式、每个文件的同步决策流程、写入路径与校验、性能模型与已知限制。

## 1. 设计目标与基本约束

常规同步工具以文件为单位：2 GB 的文件改 100 字节也要重写整个文件。blocksync 把文件切分成固定大小的块，逐块记录 SHA-256，按块判断差异，只写变化的区间。由此导出两条基本约束，全文其余部分都在围绕它们展开：

- **索引与数据分离**。数据文件完全不动，哈希索引放在每个目录自己的 `.blocksync` 子目录里，随磁盘移动；这样换机器、换盘符后索引仍能被找到并继续使用。
- **索引是判断依据**。只要两侧索引与磁盘现状一致（大小、修改时间、块参数都吻合），比较哈希即可得出差异，不需要读任何文件内容；一旦不一致才退化为重扫。

## 2. 架构与包结构

```text
cmd/blocksync          命令行入口：五个子命令的所有参数解析与交互确认
cmd/blocksync-ui       图形界面：Win32 外壳，同步逻辑完全委托 CLI（见《图形界面》）
internal/scan          目录遍历、排除规则、并行块哈希、差异区间计算、单遍复制
internal/index         每文件块索引的编码、解码、ContentDigest、原子存储
internal/state         目录锁、本机配置 config.json
internal/mirror        目录到目录同步主流程：决策、写入、删除、索引维护、源目录保护
internal/version       程序版本号，CLI 与 GUI 共用的唯一定义处
```

依赖方向为单向：`cmd → mirror → scan/index/state`，没有反向依赖与包间循环。

### 2.1 同步目录内的状态布局

两个目录同步时各自维护一份状态，全部放在目录内的 `.blocksync` 子目录（本身被排除，不进入同步范围）：

```text
<目录>\.blocksync\
  lock             单实例锁文件，内容为 pid 与占用时间
  idx\<相对路径>.idx   每个同步文件一份块索引，目录层级与被同步目录完全对应
```

索引按相对路径逐文件独立存放，好处是单个索引损坏只影响一个文件（降级为重扫），不会殃及整个目录的元数据。

### 2.2 本机配置

`%LOCALAPPDATA%\blocksync\config.json` 保存生效目录对、按目录对的排除规则与具名配置，结构见《排除列表》。它不随同步目录移动，仅对当前机器有意义。

## 3. 两级分块与哈希

| 参数 | 默认值 | 选项 | 含义 |
|---|---|---|---|
| 粗块 LB | 4 MiB | `--lb` | 索引中的粗粒度块，参与 `ContentDigest` |
| 细块 SB | 32 KiB | `--sb` | 最小比对与写入单位，决定写入放大的下限 |

合法性约束（`scan.ValidateBlocks`）：`LB > SB` 且 `LB % SB == 0`。文件按 SB 切分时最后一块允许不足额。两侧的 `LB/SB` 必须一致：索引头里记录了这两个值，不一致时索引直接按失效处理，退化为重扫；`mirror.Run` 还会把「块大小不同」写进日志原因（见 §5.4）。

哈希算法是 SHA-256，摘要定长 32 字节（`index.HashLen`）。

### 3.1 一次读取算两级哈希（scan/hash.go 的 `mapLBs`）

扫描的核心是 `mapLBs`：以 LB 为作业粒度的并行流水线。

- 每个工作 goroutine 持有一个 **LB 大小的读缓冲**（默认 4 MiB），用 `ReadAt` 按 LB 原子偏移读取，因此 LB 内的两次哈希（整体一次、每个 SB 一次）都直接在内存缓冲上进行，不产生第二次 IO。
- 读入一个 LB 后先对整块求一次 SHA-256，再对其中每个 SB 求一次，写入 `lbHashes{idx, lb, sb[]}` 经 results 通道交还；每字节数据大约参与两遍哈希计算，CPU 开销约为单遍哈希的两倍——这是 `--workers` 默认取 CPU 核数（`runtime.NumCPU`）的原因。
- 并行度以 LB 为粒度：作业数不足时自动收缩 worker 数到块数；错误只记第一次（`sync.Once`），最后统一返回。
- `ScanFull` 把同一 worker 回调写入两套哈希表后，将 **整个文件** 即一个 `[0, size)` 区间标记为「变更」；`ScanDiff` 在 worker 回调里额外做本 LB 内的逐 SB 哈希比较（见 §6）。

### 3.2 粗块哈希的用途

**差异定位只用细块哈希**。索引里的粗块哈希只参与 `ContentDigest`（整文件内容摘要）的计算，不用于跳过读取。这一点决定了「一个 LB 内只改一小段」的成本：该 LB 无论改多少，逐个细块哈希反正要做一遍，实际节省的是写入端。

## 4. 索引格式（internal/index）

每个文件一个 `.idx`，内容全为小端序。固定头 56 字节 + 两张哈希表：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 8 | 魔数 `BLKIDX2\0` |
| 8 | 4 | 版本号，当前为 2 |
| 12 | 4 | 粗块大小 LB（字节） |
| 16 | 4 | 细块大小 SB（字节） |
| 20 | 4 | 哈希长度，固定 32 |
| 24 | 8 | 该文件的长度（字节） |
| 32 | 8 | 修改时间（Unix 纳秒） |
| 40 | 8 | 粗块数 `nLB` |
| 48 | 8 | 细块数 `nSB` |
| 56 | 32·nLB | 粗块哈希表 |
| 56+32·nLB | 32·nSB | 细块哈希表 |

解码时逐项校验：魔数、版本、哈希长度，并且 `nLB/nSB` 必须与 `ceil(Size/LB)`、`ceil(Size/SB)` 吻合、总长度与块数精确相等——任何一处不符即判为「索引损坏」。损坏不会中止同步：mirror 会打印警告并按无索引重新扫描该文件。版本 2 之前的索引（旧魔数/旧布局）会按损坏处理，同步时自动重扫重建；直接跑 `verify` 会报「索引损坏」，先 `repair` 即可。

### 4.1 体积估算

```text
索引 ≈ 56 + 32·ceil(size/LB) + 32·ceil(size/SB)
     ≈ 56 + size/131072 + size/1024
     ≈ size × 0.00098　（约数据的 1/1024）
```

200 GB 数据约对应 200 MB 索引。这同时意味着 **每次重写索引本身就是一次可观写入**，所以「未变化的文件不重写索引」是一条刻意的节省路径（见 §7）。

### 4.2 内容摘要

**`ContentDigest`**（`File.ContentDigest`）对 LB、SB、长度与两张哈希表求 SHA-256，**不含 mtime**。所以仅仅碰一下修改时间不会改变内容摘要，`verify` 的比对不受 mtime 影响。

### 4.3 存储方式（`index.Store`）

保存逻辑为「写 `*.idx.tmp` 再 `os.Rename`」的原子替换，崩溃不会留下半个索引；`Load` 读到不存在的文件返回 `(nil, nil)`，损坏则报错由调用方降级。`List` 返回全部已建索引的相对路径，供镜像结束时清理磁盘上已不存在的残留条目。

## 5. 目录到目录同步的决策流程（internal/mirror）

同步主流程为 `mirror.Run`，对每对目录执行一遍；文件之间**串行**处理，单个文件内部的哈希**并行**。为什么文件间不并行：块操作的收益集中在单个大文件上，文件间并行会让多个 worker 共争磁盘顺序带宽，小文件多时反而更受每文件 stat 与索引读写开销支配。

### 5.1 目录扫描与配对

两侧先各自 `Walk`（遵守排除规则，见《排除列表》），得到按相对路径排序的文件清单。配对按 `scan.PathKey` 比较：Windows 下忽略大小写。被排除规则命中的条目两侧都不进入文件清单，因此既不比较、不建索引，也不会被镜像删除，只在最终日志的「按排除规则跳过」行里列出。源端扫描（`WalkStats`）还会跳过非普通文件（符号链接、设备文件等），同样计入跳过列表。

目标侧有、源侧没有的条目进入 `dels` 列表，按镜像语义将被删除。

### 5.2 两侧索引的「新鲜」判定

对每个文件的源、目标索引各判一次「新鲜」：

```text
新鲜 = 索引存在且可解码
     且 Size 与磁盘当前一致
     且 MtimeNano 与磁盘当前一致
     且 LB/SB 与本次运行参数一致
```

**目标侧的「新鲜」先于源侧判定并且是硬前提**：即使源索引新鲜，只要目标侧文件在磁盘上变了（大小/时间与目标索引不吻合），就必须先对目标全文件 `ScanFull` 重扫一次拿到真实的哈希，否则按过期哈希算区间会写错内容。这次重扫的读取量记入报告（dry-run 也同样计入）。

### 5.3 逐文件决策表

| 源索引 | 目标文件 | 处理方式 | 源读取 | 目标读取 | 写入 |
|---|---|---|---|---|---|
| 新鲜 | 存在且索引新鲜 | 两份索引逐细块比（`RangesAgainst`） | 0 | 0 | 变化区间 |
| 新鲜 | 存在但索引失效 | 先 `ScanFull` 重扫目标，再按两份索引比 | 0 | 目标全文件 | 变化区间 |
| 新鲜 | 不存在 | 索引给出全文件区间，直接从源复制 | 全文件 | 0 | 全文件 |
| 失效 | 不存在 | `CopyFull`：一遍读取同时复制并建索引（不并行哈希） | 全文件 | 0 | 全文件 |
| 失效 | 存在（索引无论新旧） | `ScanDiff`：重读源生成哈希，与目标索引逐细块比 | 全文件 | 视目标索引 | 变化区间 |

`--full` 的效果是把源索引一律按失效处理。两条补充规则：

- **空文件与截断保护**：`needWrite = 有变化块 或 目标不存在 或 目标长度≠源长度`。零长度文件（「清空」）与文件缩短（「截断」）即使没有变化块也会进来一次写操作，否则截断会丢。
- **源侧为何仍要重写的输出**（`srcWhy`）：目标有该文件但源索引不可复用时，日志给出括号原因：`全量比对`、`源索引不存在`、`源文件长度变化`、`源文件修改时间变化`、`块大小不同`、`源索引不可用`。这是排查「为什么没省下来读取」最直接的一手信息。

### 5.4 首次同步与计划确认

实际写入发生前会基于**文件列表与元数据**（不读内容）生成 `Plan`：目标 `.blocksync` 不存在记为 FirstRun，新文件、大小变化、需比对、待删除的个数与体积各计一行。`Plan.NeedsConfirm()` 为真（首次同步或含删除）时 CLI 弹出确认、GUI 弹出确认框——确认框内容即这段摘要，这正是 GUI 依靠 `需要确认后才会开始写入` 这行文本驱动弹窗的原因（文本内容在两侧保持一致，属对外契约）。

删除数量还有一道独立安全闸：`checkMassDelete` 的上限取 `max(100, 源文件总数×1%)`，超过时报错并要求 `--allow-mass-delete` 才继续，用于兜住「方向写反/根目录选错」这类最危险的事故。dry-run 不执行该检查（它本来就不删）。

## 6. 差异区间的计算

### 6.1 `ScanDiff`（源侧索引失效时）

`mapLBs` 读入每个 LB 的同时做该 LB 内的逐 SB 比较，连续变更合并成一个区间：

```text
对 LB 的每个细块 j：
  与旧索引同序号的细块哈希相同 → 结束当前区间（flush）
  不同（或旧索引对应块越界/不存在）→ 并入当前区间
```

这使区间天然「对齐 SB、不跨 LB 边界」。两个特化：

- 全部细块都变了 ⇒ 直接给单个 `[0, size)` 区间，避免产生海量碎块。
- 变更量为 0 的文件不会有任何写入，但索引是否重写另算（见 §7）。

### 6.2 `RangesAgainst`（两侧索引都新鲜时，`mirror` 中使用）

两份索引直接比较，允许长度不同（文件变长或变短）：

- 旧索引（目标侧）没有覆盖的新增块一律按变更算；
- 新旧长度不同 ⇒ 多出的尾巴不生成「删除」区间，由写入端的最终 `Truncate` 一次到源长度实现；
- 两侧块参数不一致 ⇒ 返回全文件单个区间（等价于重写）。

因为比较位置是「固定偏移的细块」，文件中间插入或删除字节会让之后的内容整体位移，位移之后**全部判为变化**。这就是 Office 文档（docx/xlsx 每次保存重新打包）只改一个字却几乎全量写入的原因，属于按偏移比对的固有代价；虚拟机磁盘随机改写则正好受益。

### 6.3 写入时目标截断

`copyRanges` 写完所有区间后总是 `Truncate` 到源长度、`Sync`、用 `Chtimes` 把目标 mtime 还原成源的。这使得「长度变化」自动收敛为一次恒定的元数据操作 + 变化区间的写，而不是整文件重写。

## 7. 写入路径与索引维护

### 7.1 两条写路径

- **`CopyFull`（全新文件）**：单遍顺序读，边写目标边算 LB/SB 哈希（哈希在复制线程内同步做，不并行，避免与写 IO 争抢），最后 `Truncate` 到源长度、`Sync`、还原 mtime。新文件且源索引不可信时走它，不再退化为「先扫后拷」两遍读。
- **`copyRanges`（已有文件）**：打开目标（`O_CREATE|O_RDWR`，不截断），对每个区间用 4 MiB 缓冲 `ReadAt`/`WriteAt` 循环搬运，最后截断与还原 mtime。目标文件已存在时按区间覆盖写入，宁可局部写也不整体重写。

### 7.2 写后校验（`--verify`）

每个实际写过（或整份复制）的目标文件，立即再对目标做一次 `ScanFull`，与新得到的源索引比较 `EqualContent`（等价于比 `ContentDigest`，不含 mtime）。不一致立即报 `写入后内容与源不一致` 并中止，不再继续其余文件。代价是重读本次写过的全部数据。

### 7.3 索引的写回与失效

- 源侧索引用**源文件的 mtime** 保存；目标侧索引用**目标文件的实际 mtime** 保存（写入后 `os.Stat` 一次，文件系统会取整纳秒）。`saveIndex` 直接改写索引对象的时间字段，不再复制整份索引；`Store.Save` 顺序流式写出「头部 + 两张哈希表」，也不在内存里再拼一份完整缓冲。单个文件的存活索引因此是「源、目标、新扫描」三份，写盘时不再额外翻倍。
- 未变化且索引有效的文件**不重写任何索引**，这是重复同步近零 IO 的关键。
- 删除文件时同步删除目标侧 `.idx`。
- 同步结束时把两侧索引目录收缩到源文件集合，删除磁盘上已不存在的残留条目。
- 进程在写入中途被终止时，已写入的区间不会回滚；下次运行因目标 mtime/大小变化使目标索引失效，自动重扫目标并按实际内容补齐（即「自愈」，不需要人工 repair）。
- `.blocksync\lock` 用 `O_EXCL` 创建保证单实例（见《源目录保护》）。

## 8. 一致性、锁与并发

| 机制 | 做法 |
|---|---|
| 单实例 | `.blocksync\lock` 以 `O_EXCL` 创建，含 pid 与时间；`sync` 同时对两侧加锁，任一侧已被占用即失败；`--force` 可强制接管 |
| 原子写 | 索引与文件先写 `.tmp` 再改名 |
| 半写恢复 | 数据区间不回滚：中断后目标 mtime/长度必变，目标索引自动失效，下次重扫并补齐 |
| 并发模型 | 文件间串行，文件内按 LB 分块交给 `--workers` 个 goroutine |

## 9. 性能模型

单文件成本的三部分：

```text
读放大：两份索引都新鲜时 0；否则读取整个文件 size
写量：  变更细块数 × SB（区间合并后仍按 SB 对齐）
索引：  每次该文件有写入时约 size/1024 重写一次；未变化文件不写
CPU：   每次需要重扫时 ≈ 2 × size 字节的 SHA-256（两级各算一遍）
```

只统计数据文件的读写，不含 `.idx` 的自读写。

| 场景 | 源读取 | 目标读取 | 写入 | 索引重写 |
|---|---|---|---|---|
| 两份索引都有效、内容一致 | 0 | 0 | 0 | 无 |
| 两份索引都有效、部分块变化 | 0 | 0 | 变化区间 | 两侧约 size/1024 |
| 2 GB 文件改 100 KB（mtime 变） | 2 GB | 0 | ≈100 KiB+（按 SB 对齐） | 约 2 MiB |
| 首次同步 | size | 0 | size | 约 size/1024 |
| 目标被外部改动 | 视源索引 | size（重扫目标） | 变化区间 | 两侧 |
| dry-run（目标索引也失效） | 视源索引 | size | 0 | 无 |

由此推出几条实用规律：

- **重复同步几乎零读**。只有两份索引都新鲜才能零读，同步完成后的接近时刻反向同步最省；反过来，曾被外部程序改动过的文件（哪怕只动一个字节）都会触发一次全文件重扫。
- **省的是写入量，不是读取量**。源文件 mtime 变一次，就要整文件重读一遍重算哈希。对「读得快、写得慢」的介质（如本地 SSD → USB 硬盘），这个折中通常是划算的。
- **写入放大有下限**。SB 对齐后，5×4 KiB 的零散改动会产生 5×32 KiB 的写入（≈3.2×）；`模拟改动.ps1` 正是为此设计了块对齐模式来估计这个数字。两端统一改小 `--sb`（如 16384）能减小放大但会增加索引体积（翻倍）与哈希 CPU 开销，需按实际负载评估。
- **整段顺序改写回归全量**。连续顺序改写大文件（如整体转码一遍视频）会让几乎全部细块哈希变化，等效于全量写入——块级增量的收益条件是「改动的偏移范围有限」，而不是「字节数少」。

## 10. 已知限制

- 只同步**文件内容**：不处理权限、ACL、文件属性、备用数据流、符号链接与硬链接；空目录不会创建/清理（除非经由文件路径顺带建立）。
- 按固定偏移比对：文件中间插入/删除字节会让其后全部判为变化（Office 文档保存接近全量写入）。
- 稀疏文件被实体化：读到的零按普通数据写入，不保留空洞。
- 快速路径依赖大小与修改时间；内容变了但 mtime 未变时必须 `--full`。Windows 高精度时间戳被复制工具拉平时也可能误判为「未变」，同上处理。
- 不支持裸设备（`\\.\PhysicalDriveN`），只处理目录树。
- 单个文件出错会中止整次同步，没有逐文件跳过并继续的选项。
- 单机方案只保存一对目录；多对目录请每次显式给路径，或用 GUI 的具名配置。
- 删除不可逆：没有回收站机制。误删防护依赖《源目录保护》中的上限与确认，不依赖事后追回，也不提供快照版本。
