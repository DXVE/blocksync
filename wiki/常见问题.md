# 常见问题

面向使用与诊断：提示语逐条解释、日志输出格式与排查流程。命令、选项与退出码见《命令参考》，工作机制见《工作原理与性能》。

## 提示语对照

按「看到这条提示时该怎么办」组织：

| 提示 | 含义与处理 |
|---|---|
| `目录不存在：…` | 盘符变化或路径填错。改用显式路径重试，或重新 `setup` |
| `目录正被另一个 blocksync 进程使用（…）` | 该目录的 `.blocksync\lock` 已被占用（锁用 `O_EXCL` 创建）。确认没有其他实例（包括 GUI）在跑之后加 `--force`；GUI 检测到锁失败时会弹窗询问一次是否强制重试 |
| `输入目录与输出目录相同` / `输出目录位于输入目录之内` / `输出目录包含输入目录` | 拓扑校验拒绝，改用互不包含的两个目录（见《源目录保护》§1） |
| `已阻止写入 …：该路径位于输入目录内` | 写入前句柄核验发现目标最终位置落进输入目录，多因运行中出现的目录联接。已中止，请检查目标子树 |
| `已阻止写入 …：该路径不在输出目录内` | 同上，目标解析出了输出目录之外的最终位置 |
| `已阻止写入 …：该文件有 N 个硬链接` | 目标是多链接文件，写入会改坏其他路径，已中止 |
| `源文件与目标文件是同一份数据，已阻止写入` | 源与目标在磁盘上是同一份数据（硬链接/联接别名） |
| `写入后内容与源不一致：…` | `--verify` 写后复算失败：介质写入不可靠或目标被并行修改。已中止整次同步 |
| `本次将删除 N 个文件… 超过安全上限` | 删除量达到事故特征值，先 `--dry-run` 确认方向与目录，再决定是否 `--allow-mass-delete` |
| `未获得确认：当前不是交互终端` | 脚本/管道场景无法回答确认，确认无误后加 `--yes` |
| `块大小非法：…` | `--lb/--sb` 不满足 `LB>SB` 且整除 |
| `警告: … 索引损坏，将重建` | 该文件 `.idx` 无法解码（魔数/长度/块数不符），忽略本条并重扫重写；个别损坏不影响其他文件 |
| `补丁校验失败：文件已损坏或被截断` | 载波上的补丁脚注 SHA-256 不匹配，拒用该份；可让对方重推 |
| `载波上的补丁与本机状态不衔接` | 本机 `SetDigest` 与载波上任何补丁的 `Parent` 不相符。`status` 查看摘要，用 `repair`+重推或让对端重推衔接（见下「分叉」） |
| `本机尚未配置` | 需要目录参数的命令没有给目录且 `setup` 未配置过，先录配置 |
| `verify` 报告 `内容不符`/`缺少索引`/`索引损坏`/`多余索引` | 逐个文件列出原因，结尾汇总不一致总数。文件内容确为最新时执行 `repair` 重建索引；或用 `--full` 同步一次让索引与磁盘重新对齐 |
| `open …: Access is denied`（recycle/系统目录下） | 检查对象是 Windows 系统目录，当前版本已内置排除；仍出现说明走了旧版程序或目录被改名 |

## 逐文件输出格式

```text
[i/N] 状态  相对路径  (说明)
```

- 状态取值：`新增`（含体积）、`更新`（`变化块 X（文件共 Y）`）、`未变`、`清空`（长度归零）、`截断`（`截断到 X`）、`删除（源端已不存在）`。
- 序号连续覆盖全部待处理文件（改动与删除），不跳号，分母 N 即「扫描 N 个」的 N。
- 已有目标文件、但源索引不可复用时行尾附括号原因：`（全量比对）`、`（源索引不存在）`、`（源文件长度变化）`、`（源文件修改时间变化）`、`（块大小不同）`、`（源索引不可用）`——用于判断读取为何没有省下来。
- 末行汇总格式（`完成：扫描 N 个，改动 N 个，删除 N 个；读取 X，写入 Y`；dry-run 为 `完成（测试比对）：…（未改动任何数据）`）是 GUI 解析状态栏与进度条所依赖的**接口格式**，改变写法要两侧同步调整（CLI 的 `confirmMarker` 常量与 GUI 的 `reResult` 正则）。

## 分叉与状态摘要

离线通道的一致性建立在 `site.json`：

- 每个站点保存 `Generation`（第几轮变更）与 `SetDigest`（整站内容摘要，按路径排序求哈希，不含 mtime——内容一致则摘要一致）。
- `status <目录> [载波目录]` 可以不联网对齐：一行看本机代次与摘要，一行看载波上其他站点的补丁数与本机「可直接应用」个数。
- 对端漏推的识别：A 端改了文件但没有 `push`，B 端 `apply` 会报 `补丁与本机状态不衔接`，并列出载波上各补丁的代次与基线摘要；在 A 端补一次 `push` 即可衔接。
- **两端分叉**（两端各自改过文件）：补丁通道无法把两个都变过的站点自动串起来，程序只报错不合并，需要人工定夺。推荐的恢复路径：把两端目录（连同各自的载波插入点）放到能同时访问的位置，用 `sync` 把内容收敛到选定的那一侧（`SetDigest` 只看内容与长度，不看 mtime，内容一致后两端摘要自然一致）；随后两端各执行一次 `repair` 对齐索引，清理载波上的旧补丁，再从 `push` 重新开始接力。日常避免分叉的根本做法是约定「同一时间只在一端改动」。

## 速度不达预期时的诊断

1. 看逐文件行的括号原因。大量 `（源文件修改时间变化）` 是正常现象——源侧任何一次改动都需要重读该文件重算哈希；大量 `（源索引不存在）` 说明索引在重建（新目录首次同步、`repair` 后）或被外部清理。
2. 结尾汇总的「读取」远大于预期而改动很小：先确认不是 `--full` 挂着；再看是否对方目录最近被外部程序碰过（哪怕只改一个字节也要重扫一侧）。
3. 「写入」接近全量而实际只改了几处：把大块的连续改动区段与实际痕迹核对（可用《演练与部署》的 `模拟改动.ps1` 对测试副本复现），常见于「文件中间插入字节导致位移」型改动（Office 保存、日志回卷），属按偏移比对的固有代价。
4. CPU 占用高属预期：两级哈希对每字节算两遍 SHA-256；`--workers` 高于核数没有收益。
