# 演练与部署

正式目录上动手之前，先在合成数据上跑通全流程、确认预期行为，是对「镜像删除」语义最有效的保护。本文说明两个演练脚本的机制与输出判读，以及迁移到正式目录的步骤。

## 1. 自动化演练：模拟测试.ps1

一条脚本在临时目录里搭建「本机 → 移动硬盘 → 另一端」三段目录，完整模拟双向往返，全程断言。数据落在 `%TEMP%\blocksync-rehearsal`，可随时删除；脚本重跑前会先清空该目录（目录名不含 `blocksync-rehearsal` 时拒绝清理，防止误删）。

```powershell
# 默认：3 个 256 MiB 文件，约 30 秒（含每个阶段的全树 SHA256 比对）
powershell -ExecutionPolicy Bypass -File 模拟测试.ps1

# 接近真实规模（注意脚本时间近似线性于数据量，规模越大越慢）
powershell -ExecutionPolicy Bypass -File 模拟测试.ps1 -FileMB 1024 -FileCount 2 -ChangeMB 200
```

脚本以 `--quiet --yes` 无人值守调用 `dist\BlockSync-CLI.exe`，每个阶段同步后对三段重新做全树哈希（排除 `.blocksync`）比对内容。共 10 组场景、21 项断言：

| 组 | 场景 | 断言要点 |
|---|---|---|
| 1 | 首次全量投递 A→D→B | 改动数 = 文件数 + 配置文件；三段树哈希一致 |
| 2 | 无改动重复同步 | 报告「已是最新」，写入量解析为 0 |
| 3 | 原地分散改写约 ChangeMB（长度不变） | 写入量大于 0、小于实际改动 3 倍、小于全量 20%；树一致 |
| 4 | 反方向第二跳 D→B | **零读取**（两侧索引都新鲜时免读的关键断言）；写量与上一跳相当 |
| 5 | 在 B 端改动后回传 B→D→A | 三段树一致 |
| 6 | 新增 + 删除 | 新增文件到达 B；被删文件从 B 消失 |
| 7 | 外部破坏单个字节 | 下次同步检测并修复 |
| 8 | 截断 5 MiB 再追加 3 MiB | 三段树一致（长度变化场景） |
| 9 | `verify` A/B | 各自报告「校验通过」 |
| 10 | `--dry-run` | 执行前后输出目录逐文件哈希完全不变 |

脚本失败即返回码 1，并保留演练数据供排查；通过后打印「全部通过（共 10 组检查）」。

### 组 3 说明了什么

组 3 是块级增量的正身检验：`Edit-InPlace` 在文件内部随机偏移写入若干 4 KiB–32 KiB 的小段（长度不变，不引起字节位移），把这 8 MiB 改动摊到 256 MiB×N 的文件上。断言 `写入 < 改动量 × 3` 同时挡住两种退化：块级机制失效（接近全量写入）和写入放大失控（区间合并没有生效）。

## 2. 块级写量预估：模拟改动.ps1

向**指定文件**原地写入若干小段随机数据（长度不变），并预先算出这些改动会命中哪些 32 KiB 块、预测同步时的写入量，可以和 `sync --dry-run` 的实测对照。

```powershell
# 仅查看计划，不写入（含随机种子，可复现同一组位置）
powershell -ExecutionPolicy Bypass -File 模拟改动.ps1 "D:\data\part-001.bin" -DryRun

# 实际写入 5 处、每处 4 KiB（默认），写入前备份为 .bak
powershell -ExecutionPolicy Bypass -File 模拟改动.ps1 "D:\data\part-001.bin" -Backup
```

| 参数 | 说明 |
|---|---|
| `-Path` | 目标文件（必填）。**会破坏其内容，仅用于测试副本** |
| `-Count` | 改动处数，默认 5 |
| `-Bytes` | 每处字节数，默认 4096 |
| `-BlockSize` | 块大小，默认 32768，需与同步时的 `--sb` 一致才能对照实测 |
| `-Seed` | 随机种子，缺省随机生成；输出会打印，凭它复现 |
| `-NoAlign` | 不再保证各处落在不同块内，用于观察跨块与放大 |
| `-DryRun` / `-Backup` | 只输出计划 / 写前复制 `.bak` |

对齐模式下，各处改动被安排到**互不相同的块**且整体保持不出块界（块内偏移 ≥1），每处只污染一个块；`-NoAlign` 则任意偏移可能跨两个块。输出三段：逐处明细（偏移、块号、块内偏移、长度、是否跨块）、汇总（数据合计 / 受影响块数 / 预期同步写入量与放大倍数）、以及建议执行的下一条 `sync --dry-run` 命令。

预期写入量的算法与《工作原理与性能》§6.1 一致：改造落在若干块内，每块按 `min(SB, 文件尾)` 计长，合计即为预测的 `变化块` 写入量。对齐模式下实测与预测应当一致（例如 5 处 × 4 KiB 预测 160.0 KiB，`--dry-run` 同步报 160.0 KiB）；偏差暴露的是区间合并或截断逻辑的问题。

## 3. 单元与端到端测试

`go test ./...` 覆盖分布在各包：排除匹配、索引编解码、区间计算、镜像主流程（含大小写与守卫回归用例）为单元测试；`cmd/blocksync/e2e_test.go` 会现场编译 CLI 并以子进程方式跑完整命令集（含退出码与错误路径）。改完代码先跑这两层，再跑脚本演练，最后才上正式目录。

## 4. 正式部署步骤

同步只写输出目录、不改输入目录——这个不对称决定了风险的方向分法：

1. **先 `--dry-run`**。重点核对结尾汇总：首次写入量应接近全量（不是错误）；已有索引时读取应远小于数据总量。逐文件行检查几个大文件的范围是否合理。
2. **先跑低风险方向：本机目录 → 目标磁盘/备份盘**。该方向任何失败只影响输出副本（输出侧本来就可能被覆盖），原数据不受影响。首次同步或出现删除前会再确认一次，别用 `--yes` 加首次跑。
3. **执行反方向（备份 → 本机）前**，先在备份目录跑 `verify` 确认副本正确；该方向会写入本机目录，首次执行前建议完整备份，或先指向一份副本目录验证后改正式目录。

部署选型速记：

| 目的 | 推荐路径 |
|---|---|
| 大文件频繁小改的持续同步 | `sync` 直连，日常加 `--verify` |
| 异常中断后怀疑状态 | `verify` → 有不一致且内容确信为最新时 `repair` |
| 无人值守排程 | `--yes` + 明确目录 + 退出码检查；保持 `--allow-mass-delete` 不常开 |
